# 旅游攻略写作

**最终产物是可执行游记。调研、比较和判断留在写作过程，正文只保留当天动作、地点、食物特色与必要提醒。**

## 先读这些

1. 仓库 `README.md` 和目标行程已有文件，确认本次范围、日期、同行人和已有准备事项。
2. 至少两篇真实历史游记，选一篇看时间轴、一篇看美食条目：
   - `content/trip/2019-xian-nanjing-hangzhou/hangzhou.md`：日期、时间、动作，用子列表列菜。
   - `content/trip/2019-xian-nanjing-hangzhou/xian.md`：`## 吃` → 街区 → 店名 → 食物、价格或短评。
   - `content/trip/2022-10-02-chongqing/README.md`：具体交通、餐馆和食物短评，注意区分当年亲历与本次计划。
3. 改写前读 [写作与验收标准](references/writing-style.md)；新建、改名或移动页面时读 [目录与校验契约](references/frontmatter-and-validation.md)。
4. 新建城市页可使用 [城市页模板](assets/city-template.md)，已有页面优先在原处修改。

历史游记只作为写法参考；旧票价、旧营业时间、当年口感评价不能直接当成本次事实。用户本轮要求优先于历史游记中的比较、感想或已取消地点列表。

## 输出结构

城市页通常按这个顺序写：

1. `# 城市／区域`，至多一句说明住宿日期、地点与人数。
2. `## 行程` → `### 月.日 地点` → 时间和动作列表。
3. `## 吃` → `### 街区` → `#### 店名` → 菜名加一句打卡理由。
4. `## 准备事项` → 证件与订单、预订、随身用品等相关类别，以 checkbox 表示。

用户要求直接执行清单时，行程项使用 `- [ ]`，时间用反引号：

```markdown
- [ ] `09:30-11:00` 清晖园，逛庭院和水景。
- [ ] `11:30-12:30` 午餐，炒牛奶、时蔬、米饭。
```

美食每条只写「菜名 + 一句具体特色／打卡理由」，地址放在店名下面一次，来源直接链接店名或地址后的短标签。正文不需要「打卡理由：」这类标签。未经亲自体验，不写「我吃过」「好吃」「一般」；不把历史游记的个人口感移植到新店。

```markdown
#### 民信老铺（华盖路店）

华盖路 119 号，逛骑楼街时顺路吃。[门店地图](已核验链接)

- [ ] 双皮奶：顺德代表奶甜品，点一碗分尝。
```

总览只保留行程概览、分类准备 checklist、必要当天提醒与分页链接。完成状态由 checkbox 记录，不在顶部再写「已确定／待预订」。未经用户确认，不替用户勾选，也不因查到有票、填好表单就标记已预订。

## 正文边界

- 删除选择对比、方案优劣、推论和研究过程，包括「怎么选」「值不值得」「本次推荐」「逐晚落脚逻辑」「不为只睡一晚付园区房溢价」等标题或段落。
- 已选行程写一条主线，不展开完整的第二套、第三套行程，也不列这次不去、不买的地方。
- 菜系百科、泛泛旅游常识、多个重复结论不进入执行页。用户要了解地方美食时，用本次沿线的店与菜直接呈现。
- 不写「建议核对所有事项」这样的空话。改成一个有对象、时间、渠道、结果的动作，如「在 12306 买 3 日返程票，检查已出票和孩子座位」。
- 保留真实影响执行的条件动作，紧跟当天步骤，用一句「遇到 X，执行 Y」写清，例如「未订到午休房，午餐后回酒店」。不给它另开比较章节。
- 不把「精简」当成删除准备事项的理由。证件、预约、漫游、现金、入境小票、雨衣、寄存取行李、儿童权益和返程接站等原有关键动作必须保留；不适用的项目才删除。
- 硬时刻按订单／官方信息，计划时段明确是安排，交通余量写「预留」。价格注明适用对象与查询日期；未知值写具体待核对动作，不填虚构数字。
- 一个事实只保留必要的一份详细说明：行程负责时间与动作，美食负责菜与特色，准备事项负责出发前完成的事。总览可有短提醒和指向详情的链接。

## 文件与层级

以仓库当前结构为准：

- `content/trip/<trip-id>/README.md`：总览、全程准备事项与分页入口；单城市游记可直接写全文。
- `<city>.md`：该城市的实际行程与地图点位。
- `<city>/<detail>.md`：已有或用户要求拆出的具体景点／办事详解，如 `zhuhai/chimelong.md`、`hongkong/banking.md`。
- `content/place/`：常驻地内容，不与出游行程混放。

保留用户已要求的父子目录和导航层级。不要把合法城市页、长隆玩法或办卡指南自动合回单文件；也不要为一段餐饮或交通信息再建主题页。移动文件时同时更新相对链接、父页面与导航，详见目录契约。

## 执行步骤

1. **确定范围**：检查工作区已有修改；读目标页和关联总览，不改无关历史游记。用 `rg` 找同地点旧记录，保留有价值的原始来源。
2. **提取执行事实**：列出日期、时间、地点、证件、订单、儿童、休息、行李和返程约束。区分用户已确认、查询结果、计划安排；这份整理不写进攻略。
3. **必要核验**：新增或更改班次、票价、开放、预约、银行规则等时，使用 `deep-research`，优先官方渠道；社媒与 Grok 只提供线索，重要结论回到原始来源。单纯改写文风且本轮已有有效证据时复用证据，不冒称重新查询。受限或无法验证的操作不编造。
4. **按历史样式重写**：时间清单、街区与店名列表、分类 checklist。把研究结论改成可执行动作，把食物介绍缩成一句特色。
5. **逐项回查**：删除的句子必须是重复、推论或过程说明；被挪走的必要动作要能找到新位置。日期、酒店晚数、票种、父子页和总览不得相互矛盾。
6. **验证**：`npm run audit-content`、`git diff --check`；按仓库要求运行 `npm run build`。用户给出页面时打开该 URL，检查正文、目录、列表与 checkbox 已显示，不能只以文件写入成功当作页面更新。
7. **交付**：简述改了什么、给文件或页面链接、报告实际验证。不要在最终回复重新粘贴已删除的比较与推论。

技能修改的回归场景和人工判定项见 [写作与验收标准](references/writing-style.md)。不需要新增配套 Agent。
