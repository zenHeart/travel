# 攻略写作技能

这个仓库里绝大多数城市攻略只有一个文件：`index.md`，按天写流水账，跟写日记一样——第几天几点做什么，写完就完事。不要把它当成一个需要"信息架构"的文档站点去设计，它是给自己和家人当天照着执行的清单。

## 先看仓库里真实的样子，不要凭直觉设计结构

`content/cities/visited/` 下随便挑几个城市（`chongqing` `xian` `nanjing` `hangzhou`）都只有一个 `index.md`，按天写：

```markdown
### 10.3 (沙坝区)

- `9:00-10:00` 楼下过早，刀削小面好吃
- `10:00-11:30` 到磁器口古镇， 23 公里，地铁 1 小时 30 分钟，打的 30 分钟
- `11:30-13:30` 磁器口，宝轮寺、大王油茶、鸡杂
```

唯一的例外是 `content/cities/visited/shenzhen/`：`index.md` 按天写主计划，另外多了一个 `nanao.md`。多这一个子页不是因为"南澳是另一个主题"，而是因为南澳/西冲穿越这一个点位本身有三套完全不同的多日玩法（自带装备露营 / 住客栈轻装 / 混合），三套方案各自两天的行程铺开来看会让主线时间轴认不出主干，所以才把"这一个点位的详细方案"单独摘出去，`index.md` 里只留一行"[方案详解](./nanao.md)"。

这是内容意义上唯一认可的拆子页理由：**某一个具体地点/景点本身有需要展开的复杂内容**（多套互斥方案、需要按小时精细规划的穿越路线之类），不是"这类信息属于同一个主题"。交通方式选哪个、住哪、预算多少、吃什么——这些从来不是拆子页的理由，它们是当天时间轴里的一句话或一个短表格。

**还有第二种拆子页的理由，跟内容复杂度无关：给地图打点。** 站点是"时间轴 + 地点"两套并行的浏览方式——时间轴就是 `index.md` 正文按天从上往下读，这是内容层面的事；地点是地图层面的事，`src/components/Map/TravelMap.tsx` 只认 frontmatter 里的 `coordinates` + `chinese_name`，写在哪个文件就在哪个文件对应坐标打一个点，点开直达那个文件。所以行程里经过的某个地理上独立、值得在地图上单独标出来的地方（比如这次跨了武汉—珠海—深圳—香港，珠海和深圳都是独立城市，值得各有一个点），需要专门开一个只带坐标 frontmatter 的子页去"认领"那个点——但这个子页只负责定位，正文写一两句概括加一个指回 `index.md` 的链接就够了，不要把时间轴内容搬过来重复一份。真正的行程叙述永远只有 `index.md` 这一份，改的时候只改那一份。

## 两条硬性规则（写完自查）

**规则一：默认一个文件，不按主题分文件。** 不要因为"这是交通信息""这是预算信息""这是准备清单"就单开 `transport.md` / `budget.md` / `hotels.md` / `food.md` / `prep.md`。航班几点、住哪家酒店、花多少钱，都写进当天那一行时间轴或紧跟其后的一两句话里，行程叙述本身永远只在 `index.md` 一处。整个行程连贯（哪怕跨了好几个城市，比如"武汉飞珠海玩两天、转深圳、去香港一天"），只要是同一次出行，叙述都放进同一个目的地的 `index.md`，按日期段落写下去，不要因为某天去了另一个城市就把那天的内容搬走——除非那一段本身就是一次不相关的独立旅行（参考 `shenzhen/index.md`：它记录的是 2017 年完全独立的一次东西冲穿越，跟这次经过深圳没关系，所以留在自己的城市目录里，不需要合并）。如果跨的某个城市值得在地图上单独有一个点（见下面"给地图打点"），可以为它开一个只带坐标、不重复叙述的定位子页，这跟"按主题分文件"是两件不同的事，不冲突。

**规则二：只有一个具体地点/景点的内容复杂到会打断主线时间轴，才把它单独拆出去**，并在主线对应那一行留一句指向子页的链接（参考 `nanao.md` 的拆法）。判断标准：这段内容如果直接铺在当天时间轴里，会不会让读者看不清"今天到底要做什么"？会的话才拆；不会的话，无论内容涉及交通、开户、订票、还是某个博物馆的注意事项，都留在主文件里。

## 两条内容硬性规则（延续上一轮）

**不写"不做什么"的排除清单。** "不去迪士尼、不买摩天轮票"这类句子信息量为零，只写实际安排了什么。真的有计划取消/推迟，在对应那一天的行程行里改一句话即可（比如把"迪士尼一日"改成"香港市区一日"），不需要专门开一段甚至专门开一个文件去解释"这次不去哪里"。

**不写论证、比较、权衡过程。** 决策阈值表、"值不值""留什么删什么"对照表、"为什么选 A 不选 B"的说理段落都不写。只写已经拍板的方案和它的关键数字（时刻、价格、地址）。需要一句话事实说明为什么没有别的选项（比如"武汉到珠海没有直达高铁"），可以带一句陈述句，但止步于陈述事实。

判断标准：读者拿着这份攻略执行时，会不会因为多读了一句话而更清楚"现在该干什么"？不会的话，那句话或那个文件就是要删的。

**规则三：合并文件时，删的是"文件边界"和"论证过程"，不是内容本身。** 把多个主题子页合并回一个 `index.md` 是结构性操作，不等于要把内容也压缩变薄——原来单开一页讲清楚的东西（比如开户要交什么材料、失败了去哪个分行、进园前要核对身高和推车规定），合并之后应该原样搬进对应那一天的行程里，只是不再单独占一个文件、不再重复表述，绝不能因为"要精简"就顺手把这些必须执行的准备步骤和清单一起删掉。写完对照一遍：被删掉的每一句话，是"论证/比较/排除清单"（该删），还是"用户真的要照做的一个步骤或一条数字"（不该删，只能搬家）？分不清就把原文贴回去，而不是猜一个更短的版本。

## 核心工作流

1. **确认这次改动是不是同一次出行**：先看目标城市目录下现有文件全貌（`ls` + 读该目录下**每一个**文件，不只读 `index.md`）。如果目录里已经有好几个主题子页（说明之前拆分错了），先把内容合并回 `index.md`，删掉多余文件，再改内容——不要在错误的结构上继续添砖加瓦。合并时先把要合并的子页整篇读完，把里面的具体数字、步骤、清单原样搬到对应天数下面，再删文件；不要凭对该子页内容的印象/摘要去重写一遍更短的版本，那样极易把准备步骤当废话删掉。
2. **动笔前搜一遍这个地方在仓库里有没有别的记录**：`grep -rl "地名" content/cities/` 看看 `wishlist/` `planned/` 里是不是已经有人写过这个城市/景点（比如提前存过官方票价、避坑顺序、套餐参考价）。这些是真实攒下来的一手信息，直接搬进新行程里，不要凭自己现查的资料重新写一遍、把已有的具体数字和实操经验漏掉。如果这次行程让某个 `wishlist` 条目从"想去"变成"真的要去了"，提醒用户这个旧条目是否需要合并或清掉，不要留着两份内容各说各话。
3. **检查这次改动会不会连累目录里不属于这次行程的文件**：比如目录里混着一份跟这次出行无关的旧记录（历史游玩笔记）。这类文件本来可能靠"旁边还有很多同类子页"或者一句嵌在正文里的说明来表明自己无关；一旦这次改动把其它子页都清空、只剩它自己，它原来的标记方式可能就不够用了。删完其它文件后，回头看一眼还留着的每个文件，确认光看标题/frontmatter就能看出它是历史记录还是本次行程的一部分，不要求读者去读正文第一句才能确认。
4. **该核实的事实先核实**：航班/高铁班次、票价、场馆开放时间、接驳耗时、购票预售窗口、办事流程（银行开户之类）——不能凭经验编。调用 `deep-research` 技能查证（standard 档位通常够用），把查到的具体数字、班次号、官方链接直接写进对应那一天的行程里。用户直接给出订票 App/截图里的真实价格和时刻时，以用户提供的实时数据为准，不要用之前查到的旧数据覆盖它。涉及"怎么操作能最省事/最快"这类最佳实践问题（比如提前在 App 上做完哪一步能省掉现场排队），deep-research 查到的官方页面往往语焉不详，用 `kimi-webbridge` 拿真实浏览器核实实际 App/网页流程、小红书或知乎的真实操作耗时反馈，把结论落成具体动作。查不到就写"待核实"，不要用"大约""应该是"填空。
5. **按天写，用 `` `HH:MM-HH:MM` `` 或 `` `HH:MM` `` 反引号包裹时间**，后面直接跟动作，参考仓库里其他城市 `index.md` 的既有写法：

   ```markdown
   ### 09.25（五）

   - `08:30-09:30` 早餐，按开园时间入园
   - `09:30-12:00` 鲸鲨馆
   - `12:00-15:00` 午餐，回房午休（珠海长隆企鹅酒店）
   ```

   酒店、票价、交通方式这些信息直接嵌进对应那一行或紧跟一句话，不新开表格、不新开文件。改了某一天的关键事实（比如换了航班、到达时间变晚了），要顺着影响链往后看：会不会导致次日安排也要跟着调整（比如深夜才到店，第二天就不该再写"早起入园"）。
6. **跑校验**：`npm run audit-content`。这个脚本会抓 frontmatter 缺字段、坐标越界/重叠、站内死链、死图、正文过短、以及一个极易踩的中文加粗渲染坏例（见 `references/frontmatter-and-validation.md`）。改完必须跑到 `✓ 内容层无问题` 才算完工。

## 什么时候触发

- 用户要新建一个城市攻略，或把某次行程讨论整理成攻略。
- 用户要求"按现有风格改写"、"剔除过程性描述"、"重构成可执行版"、"删掉某个子页/章节"。
- 行程发生变化（日期、交通方式、人员分组变了），需要把改动同步到对应天数的行程里。
- 发现某个城市目录被拆成了一堆主题子页——这本身就是需要修的问题，主动提出合并回单文件。

## 参考模板

`references/templates/index-template.md` 是一份去掉具体城市内容的单文件骨架，新建城市攻略时可以从它起手。`references/frontmatter-and-validation.md` 是 frontmatter 契约和校验脚本的检查清单。
